    技术复盘

    券序如何在消息不可用时恢复建单

    应用先将下单意图写入 MySQL，再用 Redis Lua 按订单标识预占库存。消费者在同一事务内建单和条件扣减 MySQL 库存。消息发送与数据库恢复分别调度，避免把恢复进度绑在 Broker 上。

    超时关单由延迟消息触发，数据库按截止时间和主键补扫。关单事务登记库存释放任务，Redis 按原订单标识幂等释放。生成列唯一索引限制同一客户同一券的有效订单，取消记录可以保留。

    本机实验中，Broker 停止约 5 分钟期间受理的 12 笔请求，在 Broker 重启前由恢复任务建单，停写后 Redis 和 MySQL 库存一致。

    规则已能分流，Agent 还能帮客服做什么

    规则根据订单状态和申请类型确定处理路径。人工复核时，Agent 整理订单事实、客户陈述、政策原文和待核查事项。客服核实材料后提交结论，工单状态由业务服务更新。

    模型调用在数据库事务外执行。执行器回写前校验任务状态、租约与令牌，避免过期执行者覆盖新结果。报告还会核对政策引用是否来自本次检索，以及原文是否一致。

    基于 Olist 公开评论改写的 40 条留出案例，两版离线回放的合格报告由 28 条增至 32 条。其中 7 条新达标，3 条退步。
